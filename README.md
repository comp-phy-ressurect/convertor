# DevConvert

DevConvert is a static, browser-only toolbox of developer converters — 25 tools. It converts between JSON, YAML, TOML, CSV, TSV, XML and HTML tables in any direction, and covers JSON Schema, TypeScript, Zod, Python, Go, SQL, JWT, Base64, URL encoding, cURL translation, hashes, timestamps, UUIDs, ULIDs, case conversion, regex testing and diffing. There is no backend, no build step and no framework: the whole application is plain ES modules served as static files. Every conversion is parsed and generated by JavaScript running in your own tab, so nothing you paste, drop or open is uploaded anywhere.

---

## Run it locally

```
python3 -m http.server 8080
```

On Windows:

```
py -m http.server 8080
```

Then open:

- the app — `http://localhost:8080/`
- the test harness — `http://localhost:8080/tests/`

**Why a server is required.** Opening `index.html` by double-clicking it gives the page a `file://` origin, and browsers treat every `file://` document as an opaque origin for CORS purposes. Two things break immediately:

- **ES modules.** `<script type="module">` and every `import` inside it are fetched with CORS semantics. Under `file://` the fetch is rejected, so `src/app.js` never loads and the page stays on its static no-JS fallback.
- **Web Workers.** `new Worker(new URL('./regex-worker.js', import.meta.url), { type: 'module' })` in `src/workers/regex-client.js` fails for the same reason, so the regex timeout protection is unavailable.

Any static file server works — `python3 -m http.server`, `npx serve`, `caddy file-server`, nginx. There is nothing to compile.

## Architecture

```
index.html            static shell + no-JS fallback content
privacy.html          Privacy Policy (no app JS)
terms.html            Terms of Use (no app JS)
<slug>/index.html     one generated static entry page per tool
styles/main.css       all styling, no preprocessor
src/
  app.js              application controller
  config.js           deployment knobs, feature flags, limits, storage keys
  tool-registry.js    single source of truth for every tool
  detect.js           input-type detectors
  router.js           History API routing
  storage.js          history, presets, settings (localStorage)
  files.js            local file reading and downloading
  security.js         size policy, safe DOM helpers, identifier/literal escaping
  vendor.js           the only file that imports third-party code
  ui.js               all DOM construction
  converters/         pure conversion functions
  workers/            Web Worker plumbing
vendor/               version-pinned ESM copies of every dependency
tests/                zero-dependency browser test harness
scripts/build-seo.mjs   regenerates entry pages, sitemap.xml and robots.txt
_headers              CSP and cache headers (Cloudflare Pages / Netlify)
sitemap.xml           generated
robots.txt            generated
.nojekyll             stops GitHub Pages dropping _headers
```

| Module | Purpose |
| --- | --- |
| `src/config.js` | Deployment knobs: production origin, base path, feature flags, limits, storage keys. Change the domain here. |
| `src/app.js` | Controller. Wires registry, router, storage and UI together; the only module that owns mutable state. |
| `src/ui.js` | All DOM construction. The only file that touches the DOM. |
| `src/tool-registry.js` | Single source of truth for tools: identity, copy, options schema, example, download extension, limitations and the `run` function. |
| `src/detect.js` | Independent scoring detectors that guess what you pasted (`{ type, confidence, reason }`). Detection only *suggests* a tool; a manual choice always wins. |
| `src/router.js` | History API routing over real, crawlable paths — no hash routing. `/json-to-yaml/` is a genuine URL and a real file on disk. |
| `src/storage.js` | History, presets and settings in `localStorage`, with a memory fallback for private-browsing and quota failures. |
| `src/files.js` | File API reads, size policy enforcement, Blob downloads, clipboard. No upload path exists. |
| `src/security.js` | Size classification, `textContent`-only DOM helpers, and correct escaping for generated JS/TS/Python/Go/SQL. |
| `src/vendor.js` | The only file importing third-party code. Every dependency is re-exported through a narrow façade. |
| `src/converters/*` | Pure functions: input string plus options in, result object out. |
| `src/converters/formats.js` | The format matrix. Each format declares `parse` and `serialize`, so conversion is `serialize(to, parse(from, text))` — N formats give N×N conversions. |
| `src/converters/xml.js` | Hand-written XML parser and serializer. No `DOMParser`, deliberately: it does not exist in a Web Worker. |
| `src/workers/*` | Web Worker plumbing. `regex-client.js` spawns a fresh worker per run and terminates it on a 750 ms timeout — a worker stuck in catastrophic backtracking can only be killed, never recovered. `transform-client.js` keeps one long-lived worker and only uses it above 512 KiB, since ordinary converters always terminate. |

### The format matrix

Seven formats — JSON, YAML, TOML, CSV, TSV, XML and HTML tables — are declared in `src/converters/formats.js`, each with a `parse` and a `serialize`. Conversion is composition:

```js
serialize(to, parse(from, text))
```

So 7 formats give 49 working conversions from 7 pairs of functions, and adding an eighth format adds 15 more conversions without touching any converter. The pane headers *are* the format selectors, so any pair is reachable in two clicks.

The pairwise pages (`/json-to-yaml/`, `/csv-to-json/`, …) are presets over this same machinery: they differ only in which formats start selected and in the copy their landing page carries. Changing a selector navigates to the page named after that pair when one exists, and to `/convert/` when it does not — so the URL never claims to be a JSON → CSV page while producing XML.

The cost of a common representation is that each format's quirks must be surfaced rather than absorbed: TOML has no null, tables have no nesting, XML and CSV carry no types. `describeConversion()` can describe a lossy pairing before it runs, and each serializer records what it had to do afterwards — both are part of the API and covered by tests, though the UI does not print them. A test asserts the matrix and the original pairwise converters produce byte-identical output, which is what stops the two paths drifting apart.

### Why the transform worker transfers bytes, not strings

`transform-client.js` hands the worker an `ArrayBuffer` and gets one back, rather than passing the input and output strings directly. That is not premature optimization — the first implementation did pass strings, and it was measurably *worse than no worker at all*:

| 560 KiB JSON → YAML | Time |
| --- | --- |
| Main thread, no worker | ~650 ms |
| Worker, passing strings | ~1180 ms |
| Worker, transferring buffers | ~185 ms |

The reason is that `postMessage` **copies** whatever you give it via structured clone, and that copy happens on the sending thread. Cloning half a megabyte of string on the main thread is precisely the stall the worker was supposed to remove, and it is paid twice — once on the way in, once on the way out. Transferring an `ArrayBuffer` moves ownership in constant time instead.

If you add a converter to the worker's dispatch table, keep the buffer discipline.

### Why the UI stays quiet

Converters return `notes` and `warnings`, and most registry entries carry a `limitations` array. **None of them are rendered in the app.** The status line shows one thing on success — `✓ Converted` — and the options panel hides every control that does not apply to the selected formats.

This is deliberate. A conversion that worked should read as a result, not as a lecture; a panel that prefixes every successful JSON → TOML with *"TOML cannot have an array at the root, so the records were wrapped"* trains people to ignore the panel entirely, which is exactly when a real message stops landing.

The information is not thrown away. It is still returned, still asserted on in the tests, and still surfaced where it earns its place:

| What | Where it still appears |
| --- | --- |
| `tool.limitations` | The static SEO landing page for each tool, under "Good to know" |
| MD5 / SHA-1 "not secure" | Next to the algorithm checkbox in the options panel |
| JWT "signature not verified" | A persistent banner above the panes |
| Errors | The status line, in full, with line, column and hint |
| Oversized input, streamed CSV, regex running without its timeout | The status line, because each changes what you actually got back |

If you want the notes back, `renderStatus()` in `src/ui.js` is the single place to restore them.

### The key invariant

**Converters are pure and DOM-free.** A converter receives a string and an options object and returns a result object. It never reads `document`, never writes to the page, never touches storage and never performs I/O.

That single rule is what makes two things possible:

1. The test harness at `/tests/` can import and exercise every converter directly, with no DOM fixtures and no headless browser automation.
2. The same module can be imported inside a Web Worker, which is how the regex tester gets a real 750 ms timeout instead of freezing the tab.

The corollary is that adding a converter never means editing `ui.js` — the UI renders itself entirely from the registry's options schema.

## Privacy model

This section is deliberately precise about both what is true and what is not.

**What the application does.**

- Converter input, dropped and opened files, and generated output are processed locally by JavaScript in your tab. The application code in `src/` contains no `fetch`, no `XMLHttpRequest`, no `navigator.sendBeacon`, no form submission and no third-party API call. `files.js` reads files with the File API and produces downloads from an in-memory `Blob` and a revoked object URL — there is no upload code path to invoke.
- Dependencies are **vendored** under `/vendor` as version-pinned ESM bundles, so no CDN request is made at runtime and no library provider ever sees your input. (Papa Parse ships a remote-download code path built on `XMLHttpRequest` for its `download: true` option; DevConvert never passes that option, and the production CSP's `connect-src 'none'` blocks it regardless.)
- History and presets live in `localStorage` on this device only, under the keys `devconvert:history:v1`, `devconvert:presets:v1` and `devconvert:settings:v1`. History is truncated to 4 000 characters per value and capped at 20 entries by default.
- User content **never** enters the URL. `router.js` builds paths from tool slugs only. Putting a conversion in a query string would leak it into browser history, `Referer` headers and every server log along the way, so the app does not do it.
- No analytics, no advertising, no third-party trackers, no cookies set by the application.

**What this does not cover.**

Loading the page is an ordinary web request. Your hosting provider — and any CDN or reverse proxy in front of it — sees the same network metadata it sees for any website: your IP address, your user agent, the timestamp, and which URL you requested. That is outside the application's control and outside what client-side code can promise. "Your input never leaves this browser" is a claim about the *contents* of the converters, not about the existence of the HTTP request that delivered the page.

If you deploy DevConvert and later add analytics, ads or payments, that claim stops being true as written and both the README and `privacy.html` need updating.

**No dependency is used for the modern cryptographic primitives.** SHA-256, SHA-384, SHA-512 and SHA-1 are computed with the native Web Crypto API (`crypto.subtle.digest`), and UUID v4 comes from `crypto.randomUUID()`. Web Crypto requires a secure context, so hashing works on `https://` and on `http://localhost` but not on a plain-HTTP LAN address.

### Local patch to `vendor/ulid.mjs`

The vendored ulid bundle carries a local modification, noted in a comment at the top of the file:

```
/* DevConvert local patch: detectPrng() resolves Web Crypto via globalThis/self
   instead of window only, so ULID generation also works inside Web Workers and
   non-window ESM hosts. Restore the stock file from
   https://cdn.jsdelivr.net/npm/ulid@2.3.0/+esm if you need to undo this. */
```

Upstream `detectPrng()` looks for `window.crypto` and, failing that, falls back to `require('crypto')` — which does not exist in an ESM browser context or inside a Web Worker, where there is no `window`. The patch changes the root-object lookup to try `globalThis` first and then `self`, so a real CSPRNG is found in every context this app runs in.

`src/vendor.js` belt-and-braces this by also passing an explicit `globalThis.crypto.getRandomValues`-based PRNG into `factory()` and `monotonicFactory()`, so ULIDs are cryptographically random even if the detection path changes.

### Documented limitations worth knowing

Most registry entries carry a `limitations` array. It is rendered on the static SEO landing page for each tool, not in the working UI — the app deliberately keeps the panel to the conversion itself (see "Why the UI stays quiet" below). The ones most likely to surprise:

- **JWT Decoder does not verify signatures.** This is deliberate: verification needs the signing key, and fetching a JWKS would mean transmitting your token. A decoded token proves nothing about authenticity.
- **Generated code is text.** SQL, cURL translations, TypeScript, Go, Python and Zod output is never executed, and DevConvert never connects to a database or makes the request a cURL command describes.
- **Code generation infers from your sample only.** A field that is never null in the sample is typed as non-nullable; required JSON Schema fields come from which keys appear in every observed object; SQL column types carry no widths, indexes, constraints or foreign keys.
- **TOML has no null type.** Null values are dropped from the output. The JSON root must be an object.
- **CSV has no nesting.** Nested objects and arrays are serialized as JSON text inside a single cell.
- **MD5 and SHA-1 are legacy only.** MD5 is a checksum, not a secure hash; SHA-1 is broken for collision resistance.
- **Regex runs in a Web Worker and is killed after 750 ms**, and output is capped at 1 000 matches. On browsers without module workers it degrades to the main thread with no timeout, and the status line says so.
- **cURL parsing is single-command.** Shell expansion is not evaluated; pipes, redirections, subshells, `&&` chains and multiple URLs are not translated; multipart uploads and `@file` references are reported rather than converted.

## How to add a converter

1. **Write the pure function** in `src/converters/`. It takes `(input, options)` and returns a result object via the `result()` helper in `src/converters/shared.js`. It must not touch the DOM, storage, the network or the clock in a way that makes it untestable. Throw `ConversionError` with a `hint` for user-facing failures.

2. **Register the tool metadata** in `src/tool-registry.js`. This is the only place the tool is described; the SPA and the static entry pages both read it.

3. **Options render automatically.** The `options` array is a schema, not markup. `ui.js` builds the controls from `type` (`select`, `checkbox`, `number`, `text`, `flags`, `checkbox-group`), applies `parse` on the way back out, and honours `dependsOn` (react to another option) and `appliesTo` (react to the selected formats) to show or hide controls. You do not write any DOM code.

4. **Add a case to `tests/tests.js`** with an input, options and the expected output. The harness compares actual against expected and prints both on failure.

5. **Regenerate the SEO entry pages** with `node scripts/build-seo.mjs`, so `/<slug>/index.html` exists with the right `<title>`, meta description, canonical URL and `<h1>`, and so the tool appears in the crawlable no-JS list on every page.

6. **It appears in `sitemap.xml`** from the same generator pass, which also rewrites `robots.txt`. Both are derived from the registry, so there is no second list to keep in sync.

A minimal registry entry:

```js
{
  id: 'json-to-ini',
  slug: 'json-to-ini',
  label: 'JSON → INI',
  category: 'Structured data',
  description: 'Convert a flat JSON object to INI format.',
  keywords: ['ini', 'config', 'json'],
  input:  { label: 'JSON', language: 'json', example: JSON_OBJECT_EXAMPLE, accept: '.json,.txt' },
  output: { label: 'INI', extension: '.ini', language: 'ini' },
  swap: 'ini-to-json',            // optional reverse tool
  options: [
    { id: 'section', label: 'Section name', type: 'text', default: '', placeholder: 'optional' },
    { id: 'spacing', label: 'Spaces around "="', type: 'checkbox', default: false },
  ],
  limitations: [
    'INI has no nesting; nested objects become dotted section headers.',
  ],
  run: ({ input, options }) => jsonToIni(input, options),
}
```

Async converters set `isAsync: true` and return a promise. Tools that need two inputs declare `secondaryInput` (see `diff-checker`). Tools whose download extension depends on the options declare an `extensionFor(options)` function.

## Testing

```
http://localhost:8080/tests/
```

The harness is a zero-dependency browser page. It imports the pure converter and detector functions directly as ES modules, runs every case, and renders PASS/FAIL per case with the actual output next to the expected output when they differ. There is no test framework, no runner to install and no build step — open the URL and read the result.

It tests **the pure functions, not the DOM.** UI wiring, dialogs, routing and clipboard behaviour are not covered; that is a deliberate trade for having tests that run anywhere with zero setup. If a change touches `ui.js` or `app.js`, exercise it by hand.

## Deployment

The step-by-step runbook for formatport.com — host settings, header verification and analytics — lives in [`DEPLOY.md`](DEPLOY.md). This section explains the reasoning behind it.

Both targets serve the repository root as-is. There is nothing to build.

### Cloudflare Pages

1. Connect the repository.
2. Framework preset: **None**.
3. Build command: **leave empty**.
4. Build output directory: `/`.

Notes:

- `_headers` in the repository root is read by Pages and applies the Content Security Policy below. Confirm it is actually being served after the first deploy — see the checklist.
- Pages serves `/json-to-yaml/index.html` at `/json-to-yaml/` automatically, which is exactly what `router.js` expects. No rewrite rules and no `_redirects` file are needed.

### GitHub Pages

1. Push to `main`.
2. **Settings → Pages → Build and deployment → Deploy from a branch**, branch `main`, folder `/ (root)`.

Two caveats:

- **Jekyll ignores files whose names begin with an underscore.** Without intervention, `_headers` would be silently dropped from the published site. The repository already contains an empty `.nojekyll` file in the root, which disables Jekyll processing entirely; keep it. (`_headers` itself does nothing on GitHub Pages — see the next point — but it must survive so the same repository can also deploy to Cloudflare Pages.)
- **GitHub Pages cannot set custom response headers.** There is no equivalent of `_headers`, so the CSP must be delivered in the document instead. Add this to the `<head>` of `index.html` and of every static entry page, immediately after the `<meta name="viewport">` tag:

  ```html
  <meta http-equiv="Content-Security-Policy"
        content="default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'none'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'">
  ```

  A `<meta>` CSP is weaker than a header — `frame-ancestors` is ignored in meta form (which is why it is dropped above), and the policy only takes effect once the parser reaches the tag — but every other directive, including `connect-src 'none'`, is enforced. The other security headers in `_headers` (`Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`) have no `<meta>` equivalent and are simply unavailable on GitHub Pages. If they matter to you, put Cloudflare in front, or deploy to Cloudflare Pages instead.

### Changing the domain

Set `PRODUCTION_ORIGIN` in `src/config.js`:

```js
export const PRODUCTION_ORIGIN = 'https://devconvert.example';
```

Then run:

```
node scripts/build-seo.mjs
```

That rewrites every static entry page, `sitemap.xml` and `robots.txt` so that every canonical link, Open Graph URL and sitemap entry uses the new origin in one pass. It also retargets the absolute URLs in the three hand-written pages (`index.html`, `privacy.html`, `terms.html`), touching only the canonical link, `og:url` and the JSON-LD `url` — sample URLs in page copy are left alone. It is the only thing in the project that needs Node, and it is not a build step — the app itself runs straight from source. If you are deploying to a GitHub Pages *project* site rather than a user or apex site, also set `BASE_PATH` in the same file (for example `'/devconvert/'`); every internal link is built through `router.js`, so that is the only other knob.

## Content Security Policy

The policy lives in `_headers` in the repository root:

```
/*
  Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'none'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
  X-Frame-Options: DENY
  Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=(), usb=(), interest-cohort=()
  Cross-Origin-Opener-Policy: same-origin

/vendor/*
  Cache-Control: public, max-age=31536000, immutable

/styles/*
  Cache-Control: public, max-age=3600

/src/*
  Cache-Control: public, max-age=3600
```

Directive by directive:

| Directive | Effect |
| --- | --- |
| `default-src 'self'` | Fallback for everything not named below: only same-origin resources load. |
| `script-src 'self'` | JavaScript may only come from this origin. No inline scripts, no `eval`, no CDN. |
| `style-src 'self'` | CSS may only come from this origin. No inline `<style>` blocks. |
| `img-src 'self' data:` | Same-origin images plus `data:` URIs — the favicon is an inline SVG data URI. |
| `font-src 'self'` | No web fonts are loaded at all; this forbids fetching any. |
| `connect-src 'none'` | **No network connections of any kind.** `fetch`, `XMLHttpRequest`, `sendBeacon`, WebSocket and EventSource are all blocked by the browser. |
| `worker-src 'self'` | Workers must be same-origin scripts — which is how `regex-worker.js` and `transform-worker.js` are spawned. `blob:` and `data:` workers are refused. |
| `object-src 'none'` | No `<object>`, `<embed>` or `<applet>`. |
| `base-uri 'none'` | No `<base>` tag can be injected to re-point relative URLs. |
| `form-action 'none'` | No form on the page can submit anywhere. The preset form is handled entirely in JavaScript. |
| `frame-ancestors 'none'` | The site cannot be framed — clickjacking protection. `X-Frame-Options: DENY` repeats this for older browsers. |

The remaining headers are defence in depth rather than CSP: `nosniff` stops MIME-type guessing, `Referrer-Policy: no-referrer` means no page URL is ever leaked to another site, `Permissions-Policy` switches off browser capabilities the app never uses (including the `interest-cohort` opt-out), and `Cross-Origin-Opener-Policy: same-origin` isolates the browsing context. Cache rules pin the immutable version-pinned `/vendor/` bundles for a year while keeping the app's own source short-lived.

**`connect-src 'none'` is the enforcement behind the privacy claim.** Everything else in this README is a statement about what the code does; this directive is a statement about what the browser will *permit* it to do. Even if a dependency contained an exfiltration path, or a future edit accidentally introduced a `fetch`, the request would be refused by the browser and logged as a CSP violation. Auditing the claim does not require trusting the source review — it requires one `curl -I`.

**`script-src 'self'` works because there is no inline JavaScript anywhere.** `index.html` loads exactly one script, `<script type="module" src="/src/app.js">`, and every handler is attached with `addEventListener` from within a module. There are no `onclick` attributes, no inline `<script>` blocks and no `javascript:` URLs, so the policy needs no `'unsafe-inline'` and no nonce or hash machinery. The same holds for `style-src 'self'`: all styling lives in `styles/main.css`. (Dynamic per-element styles set from JS via the `style` property are not affected by CSP; only `<style>` elements and `style="..."` attributes in markup are.)

**`worker-src 'self'` and the regex timeout.** The workers are loaded from same-origin URLs — `new Worker(new URL('./regex-worker.js', import.meta.url), { type: 'module' })` — so this policy permits them.

This interaction is worth spelling out, because it is a trap. The conventional way to feature-detect module workers is to construct a throwaway worker from a `blob:` URL and observe whether the `type` option gets read. Under this policy that probe is refused, so it reports "module workers unsupported" on exactly the deployment that supports them — and the regex tester would quietly fall back to running on the main thread with **no 750 ms timeout**, which is the whole point of the worker. `regex-client.js` therefore contains no probe at all: it constructs the real worker and degrades only if that real worker genuinely fails to start or load. Verified by serving the regex tester with this exact policy applied and confirming both that matches are produced and that `(a+)+b` against 40 `a` characters still reports "Regex timed out after 750 ms".

If you ever reintroduce a probe, test it under the policy, not just in development.

## Monetization (not implemented)

Nothing in DevConvert is paid, gated or metered today. This section records what is already in place and what a paid tier would honestly require, so that nobody ships a "paywall" that is a boolean.

**Feature flags already exist.** `src/config.js` exports `FEATURES`:

```js
export const FEATURES = Object.freeze({
  ads: false,
  unlimitedHistory: false,   // 500 history entries instead of 20
  largeInputs: false,        // allow inputs above the 10 MiB reject threshold
  savedPresets: true,
  batchConversion: false,
  offlinePwa: false,
});
```

These are read by `storage.js` (history limit) and `files.js` (size policy). The file's own comment is blunt about their status, and it is right: *these are convenience switches, not a security boundary.*

**Taking a payment needs no backend.** A Stripe Payment Link or Buy Button is a hosted checkout page; you embed a link or a small script tag and Stripe handles the card, the receipt and the tax. A static site can absolutely take money. Note that the Buy Button script is loaded from `js.stripe.com`, so a checkout page would need its own relaxed CSP — keep it on a separate page rather than loosening the policy site-wide.

**A client-side `paid=true` in localStorage is a soft gate only.** Say it plainly: anyone who opens devtools and types `localStorage.setItem('devconvert:paid','true')` has unlocked every flag, in about four seconds, with no tooling. This is not a weak lock, it is a *courtesy* — a "please pay if you find this useful" that honest users respect and nobody else does. It is a legitimate choice for a tip-jar model. It is not a legitimate choice if the revenue matters.

**A signed license key works without a backend, and is genuinely stronger.** The scheme:

1. You generate an Ed25519 or ECDSA P-256 keypair once, offline.
2. When someone pays, you sign a small payload — email, purchase date, tier — with the **private** key, offline, and email them the resulting key. This can be a one-line script you run manually, or automated later.
3. The application ships only the **public** key, embedded in the source. When a key is pasted, the browser verifies the signature with `crypto.subtle.verify`. No network call, so `connect-src 'none'` stays intact and the privacy claim is unaffected.

The residual weakness is real and worth stating: a valid key can be shared. One purchase can unlock any number of browsers, and there is no way for offline verification to detect that. But forging a key requires breaking the signature scheme, which is an entirely different proposition from flipping a boolean. For a small paid tool this is usually the right point on the curve — high enough friction that casual bypass stops, low enough complexity that no server exists to maintain, breach or leak.

**Genuine payment-to-entitlement verification needs a webhook receiver.** If you need to *know* that a given browser corresponds to a completed payment — to revoke, to enforce seat counts, to handle refunds and chargebacks — something has to receive Stripe's `checkout.session.completed` webhook and issue the entitlement. The lightweight options, in ascending order of commitment: a Cloudflare Worker (fits the existing Pages deployment, costs nothing at this scale), a small server of your own, or an external licensing service such as Lemon Squeezy, Paddle or Polar that handles keys and merchant-of-record duties for you.

**Never put a Stripe secret key in frontend code.** Only publishable keys (`pk_live_…`, `pk_test_…`) and Payment Links belong in a static site. A secret key (`sk_…`) in client-side JavaScript is visible to every visitor via View Source and grants full API access to your Stripe account — refunds, payouts, customer data. The same applies to webhook signing secrets. If a piece of configuration must stay secret, it cannot live in this repository, which is the clearest possible signal that the operation it protects needs a server.
