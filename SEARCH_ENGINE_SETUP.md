## 0. Fix `www.formatport.com` first — P0

This is the one genuine defect found in production, and it should be fixed
before anything is submitted to a search engine.

**What is wrong.** `www.formatport.com` resolves to Cloudflare and completes
TLS (the zone's Universal SSL certificate already covers `*.formatport.com`),
but then returns **HTTP 522** — Cloudflare has a proxied DNS record for `www`
with nothing reachable behind it. So:

```
http://formatport.com      → 301 → https://formatport.com/   ✅ one hop
https://formatport.com     → 200                             ✅
http://www.formatport.com  → 522                             ❌
https://www.formatport.com → 522                             ❌
```

Anyone who types or links `www.` gets an error page, and any link built that
way is a wasted link.

**The fix (Cloudflare dashboard, ~2 minutes).** Redirect Rules run at the edge
*before* Cloudflare tries to reach an origin, so the broken 522 origin stops
mattering and the existing DNS record can stay exactly as it is:

1. Cloudflare dashboard → the `formatport.com` zone → **Rules → Redirect Rules**
2. **Create rule**, name it `www to apex`
3. **If** — use the expression editor:
   ```
   (http.host eq "www.formatport.com")
   ```
4. **Then** — *Dynamic* redirect:
   - Expression: `concat("https://formatport.com", http.request.uri.path)`
   - Status code: **301**
   - ✅ Preserve query string
5. Deploy.

Then confirm one clean hop, no chain:

```bash
curl -sSI https://www.formatport.com/csv-to-json/ | head -3
# expect: HTTP/1.1 301  +  location: https://formatport.com/csv-to-json/
```

**Canonical hostname is the apex, `https://formatport.com`.** Every canonical
tag, the sitemap and `PRODUCTION_ORIGIN` already agree on that; this rule makes
the network agree too.

## 1. Google Search Console

Google does **not** support IndexNow. Search Console and the sitemap are the
whole Google story.

### Add the property

1. Open <https://search.google.com/search-console>.
2. **Add property → Domain** and enter:
   ```
   formatport.com
   ```
   Domain property (not URL prefix) — it covers `http`, `https`, the apex and
   every subdomain at once, so the www fix above and any future subdomain are
   already inside it.
3. Google shows a **TXT record** to add, of the form
   `google-site-verification=…`.

   > **No token is committed in this repository, and none was invented.** The
   > value is issued by Google to your account at this step and cannot be
   > known in advance.

4. Add it in Cloudflare → the `formatport.com` zone → **DNS → Records**:

   | Field | Value |
   | --- | --- |
   | Type | `TXT` |
   | Name | `@` |
   | Content | the exact string Google showed |
   | TTL | Auto |

5. Back in Search Console, click **Verify**. Cloudflare DNS usually propagates
   in under a minute; if it fails, wait and retry rather than adding a second
   record.

### After verification

6. **Submit the sitemap.** Sitemaps → enter `sitemap.xml` → Submit.
   It should report **34 discovered URLs** and no errors. If the count differs
   from 34, `SEO_INDEX_INVENTORY.md` says what should be there.

7. **Inspect representative URLs.** URL Inspection → paste the URL → **Test
   live URL** → open *View tested page → HTML*. Confirm the rendered HTML
   contains the H1, the tool description and the related-tool links. It will —
   these are in the served HTML, not injected by JavaScript — but checking once
   proves it for the whole page family, since every tool page is built by the
   same function.

   Worth inspecting: `/`, `/csv-to-json/`, `/tools/`.

8. **Request indexing** for the list in section 3. Do the homepage first.

> The "Request indexing" quota is roughly 10–12 URLs per property per day, and
> it is a nudge, not a guarantee. The sitemap does the real work; requesting
> indexing just shortens the wait for the pages you care most about.

## 2. Bing Webmaster Tools

Bing also feeds DuckDuckGo, Ecosia and Yahoo, so it is worth more than its own
market share suggests.

1. Open <https://www.bing.com/webmasters>.
2. **Import from Google Search Console** — this is by far the easiest route and
   is why Google is set up first. It copies the verified property and the
   sitemap in one OAuth step, with no second DNS record.
3. If you would rather not connect the accounts, add the site manually as
   `https://formatport.com` and verify with a DNS TXT record the same way.
4. **Submit the sitemap** if the import did not carry it over:
   `https://formatport.com/sitemap.xml`
5. **URL Inspection** — same idea as Google's; use it on `/` and one tool page.
6. **Confirm IndexNow is linked.** Bing Webmaster Tools has an *IndexNow* page
   that shows submissions received. After the first deploy following this
   change, submissions should appear there. That page is the fastest way to
   confirm the key file is accepted.

### What to watch in Bing

Bing's **Site Explorer** shows what it has actually crawled, and its **Crawl
Information** page reports blocked URLs and fetch errors — a more direct
signal than Google's equivalent, and it usually reacts to a new site sooner.

## 4. IndexNow

Already implemented and working. This section is here so the next person knows
what they are looking at.

**What it is.** A push protocol: instead of waiting for a crawl, the site tells
participating engines that a URL changed. **Bing, Yandex, Seznam, Naver and Yep
participate. Google does not** — Google is covered by the sitemap and Search
Console above.

**The key.**

```
Key:      ed6f88db3750ce80d95587da3272e833
Key file: https://formatport.com/ed6f88db3750ce80d95587da3272e833.txt
```

The key is **public by design**. IndexNow authenticates by asking the site to
serve a file named after the key, so the key is necessarily visible to anyone
who looks. It is not a credential, it grants nothing, and committing the key
file is how the protocol is meant to be used. The only way to get it wrong is
to let the file stop being served — every submission is then rejected with 403,
which `scripts/indexnow.mjs` checks for before submitting so the failure is
legible.

**How it runs.** Deployment here is "push to `main`, Cloudflare Pages serves the
files". `.github/workflows/indexnow.yml` hooks that same event: it triggers only
when a push touches an actual page, waits for the deploy to be live, and then
submits just the URLs in that push.

**By hand:**

```bash
node scripts/indexnow.mjs --all            # every URL in sitemap.xml
node scripts/indexnow.mjs --changed HEAD~1 # pages touched since a ref
node scripts/indexnow.mjs /json-to-yaml/   # specific pages
node scripts/indexnow.mjs --all --dry-run  # show the payload, send nothing
```

Run `--all` once by hand after the first deploy that includes the key file, to
seed the engines with the full set.

**Safety properties, all tested:**

- Any URL not under `https://formatport.com/` aborts the run — a stray
  `localhost` URL can never be submitted.
- Only real pages are derived from a git diff. Changing `src/`, `styles/` or a
  `.md` file submits nothing, so routine deploys do not spam the engines.
- Deleted pages *are* submitted, which is how a URL gets dropped from an index.
- If the key file and its name disagree, it stops before the network call.
- A failed or unavailable API **warns and exits 0**. The site is already live
  and in the sitemap by then; a missed ping costs latency, not correctness, and
  is not worth failing a deploy over. Pass `--strict` when you want the
  non-zero exit.

## 5. Analytics

Already decided and documented in `DEPLOY.md` — repeated here only because
"which pages get organic traffic" is a search question.

**Cloudflare Web Analytics in server-side mode**, counted at the edge. No
`<script>`, no cookie, no beacon — which is what keeps `connect-src 'none'` in
`_headers` intact and keeps the privacy page truthful.

It answers: which page did the visitor land on, which pages get traffic, which
referrers send it. It does not answer: which tool they then used, because that
would need a client-side event, which the CSP forbids and the product promise
rules out.

**Search Console remains the primary SEO measurement source** — it is the only
one that reports queries, impressions, CTR and position. Cloudflare tells you
what happened after the click; Search Console tells you what happened before it.

**Owner action:** confirm Web Analytics is actually switched on for the zone
(dashboard → `formatport.com` → Analytics & Logs → Web Analytics). It could not
be verified from outside — edge counting is invisible in the page source, which
is the entire point.
